## Useful rendering and scheduling mechanisms

### R1. Bounded pose work with explicit cache identity — high value

**TS anchors:** `client/render/npc/AsyncNpcPoseCache.ts::{syncContext,claimActor,
enqueue,pump,run,forgetActor}`, `client/game/worker/RenderDataWorkerPool.ts`;
`client/tests/async-npc-pose.test.ts`.

The queue deduplicates pose keys, caps pending entries at 24, bounds concurrency,
prioritizes current requests over prefetch and rejects obsolete generations.
Appearance/sequence/overlay checks prevent many late results from replacing newer
poses. Actor removal explicitly drops ownership. Completed geometry can remain
GPU-resident after its CPU copy is evicted.

**Rust application:** extend the existing scene/entity catalog and renderer
projection caches; do not create another actor simulation. Key reusable poses by
cache/profile and asset generation, appearance/morph/customization, sequence
slots/cursors, interpolation mode and relevant deformation inputs. Actor-specific
pending work also needs session and actor-lifetime identity so index reuse cannot
resurrect an old pose. Share model-local geometry only where terrain contouring,
lighting and placement do not invalidate sharing.

**Limits and acceptance:** TSPS deliberately holds previous poses, permits 150 ms
cross-sequence grace and falls back to neutral geometry; those change visible
behavior and are not approved RustClient parity rules. First measure EntityBuild,
EntityUpload, duplicate poses, queued age and retained bytes. Verify cold assets,
burst updates, removals/index reuse, morph changes and device reconstruction;
compare posed geometry and picking, not just queue completion. Roadmap phases 2/6/11.

### R2. GPU rest-mesh/label pose reuse — valuable later, precision gate first

**TS anchors:** `client/render/player/LabelPose.ts::{LabelRig,LabelPose}`, NPC
GPU-pose tests and `client/tests/player-gpu-pose.test.ts::maxError`.

Eligible legacy animations upload one rest mesh plus per-label affine transforms.
Unsupported alpha/color/skeletal cases retain a CPU path. This could reduce repeated
vertex construction and upload in our entity projection.

The player test explicitly compares a floating-point reference and separately
tracks differences from the integer CPU path, which truncates after each step.
Algebraically equivalent matrices do **not** establish bit-identical stock poses.
Retain the CPU oracle until exact-240 geometry, visibility, deferred opaque depth,
face priority, contouring and picking pass. Our sorted models use posed vertices
for admission and ordering, so a shader-only pose must still supply equivalent
inputs to those consumers. Own this in scene/renderer under SPEC-0016/0007;
do not relocate sequence lifetime out of GameState. No speedup is established here.
This belongs to classic rendering phase 11 after the phase-6 actor contracts.

### R3. Cooperative builds, cancellation and coherent snapshots — high value

**TS anchors:** `client/common/utils/BuildSteps.ts::run`,
`client/rs/scene/SceneBuilder.ts` generators,
`client/game/worker/WorkerInputUpdates.ts::{hold,update}`,
`client/game/worker/RenderDataWorker.ts::cancelLoad`;
`client/tests/worker-input-updates.test.ts`.

Builds yield between smaller terrain/location units and check abort signals.
Worker inputs remain stable across yields; replaceable var/NPC snapshots coalesce,
while distinct content updates retain order. Intermediate geometry stays private.
The 8 ms yield target is cooperative, not a hard bound on a synchronous model step.

**Rust application:** our generation checks already reject late results, but they
do not stop wasted construction. Add cancellation checkpoints to existing loading
and scene-building work, with one immutable input snapshot per build. Native
threads and browser tasks implement scheduling through adapters. Latest-wins is
valid for derived projection requests, **never** for ordered packets, semantic
operations, script events or commits. Publish matching mesh, picking, metadata and
resources together. Verify rapid travel/reconnect, mid-build var changes and
cancellation cleanup. Roadmap phase 3; browser composition phase 13.

### R4. Stage large GPU uploads, then publish atomically — high value to measure

**TS anchors:** `client/render/MapGeometryUpload.ts::{step,take,dispose}`.

Copies are limited to 256 KiB per write, 2 MiB per preparation step and a
cooperative 2 ms check. `take` rejects incomplete uploads; disposal releases
partially built resources. Textures and metadata still finish before publication.

Our `GeometryGpu::create` initializes whole geometry streams synchronously, and
`update` writes each full changed stream into its retained buffer. Keep those
buffers; investigate bounded staging for large replacements instead of replacing
the resource owner. Measure upload-submission spikes and old+new peak memory.
Thresholds should follow our native/browser traces, not TSPS constants. Cancellation,
device loss and failed publication must leave a coherent drawable scene; retaining
an old scene must not allow actions against stale semantic targets. Phase 3.

### R5. Conservative visibility before costly preparation — useful with bounds

**TS anchors:** `client/render/ActorVisibility.ts::{packedActorBounds,
actorBoundsVisible}`.

Bounds include opaque and alpha geometry and reject only outside both camera and
shadow volumes. Unknown bounds/shadow information keep the actor. This is a useful
correctness pattern for our actor build cost, distinct from existing roof/zone
admission and source sorted-model rejection.

Reuse conservative cached model/pose bounds in scene projection if profiling
supports it. Never cull simulation, expiry, interactions or required asset state.
Classic rendering has no requirement to add HD shadows; if a future shadow pass
exists, camera-invisible casters must remain eligible. Test large footprints,
fractional positions, animation excursions and unknown bounds. Phases 6/11 / optional
HD after the classic baseline.

### R6. Adjacent opaque instancing, buffer pools and draw bundles — conditional

**TS anchors:** `client/render/webgpu/actors/WebGPUActors.ts::drawOpaque`,
`client/tests/webgpu-actor-batching.test.ts`,
`client/render/webgpu/actors/actorGpu.ts::ActorGeometryCache`,
`client/render/webgpu/SceneryDrawBundle.ts::draw`.

TSPS instances adjacent actors only while geometry/pipeline/actor rows/map bindings
agree; its tests deliberately keep transparent order separate. Evicted buffers
enter a size/usage pool after the preceding frame is submitted, capped at 16 MiB.
Draw bundles replay repeated command lists; changing lists remain direct.

Our renderer already merges opaque policy ranges and reuses grown dynamic buffers.
First establish pose reuse and actual draw/resource churn. Instancing must preserve
our `SortedDeferredWrite` color/depth ordering and source ties; do not batch across
that policy blindly or adopt TSPS's alpha order. A pool only helps if measured
churn remains. Bundle invalidation must include buffers, pipelines, bind groups,
MSAA/target formats, visibility and animation changes. These are renderer-owned
experiments, not new architectural boundaries or immediate roadmap prerequisites.

## Useful interface, script and RuneLite feature mechanisms

### U1. Ordered UI batching and bounded texture damage — extend existing owners

**TS anchors:** `client/widgets/gl/renderer.ts::{flushTextureBatch,
updateTextureFromCanvas}`; ordered-texture-batching tests, including the browser
readback test; `docs/runelite-performance.md`.

The renderer flushes at incompatible state changes and updates a same-size canvas
texture through a clipped damage region. Moved/removed overlays need the union of
old and new bounds so transparency clears old pixels.

Our quad atlas already reduces binds and preserves painter order; the egui shell
already retains unchanged generations. The remaining candidate is damage-aware
updates for dynamic game images/overlay targets: `DynamicTexture::upload` currently
writes a full supplied image. Add this only where counters show large uploads;
retain full uploads for resize/reconstruction. Verify overlap, masks, clip changes,
transparent erasure, scaling and disposal. Do not globally sort UI by texture or
introduce browser canvas objects into core/plugin API. Phases 7/12/13.

### U2. Interaction caching needs complete invalidation — high correctness value

**TS anchors:** `client/widgets/gl/widgetsGl/interactionMenuCache.ts::
deriveMenuEntriesForWidgetCached`, `clickTypes.ts::dropStaleClickTarget`,
`frameInput.ts::cleanupWidgetClickTarget`, `client/tests/stale-click-target.test.ts`.

TSPS keys derived entries on interaction revision, flags/mask, item, labels/actions
and operation-handler presence; current selection is considered before reuse.
Its regression cases remove stale equipment hover text and delete click targets
when scripts repeatedly replace dynamic children.

Use these scenarios when optimizing our [widget actions](../../crates/application/src/widget_actions.rs)
and [pointer projection](../../crates/game-ui/src/pointer.rs). Current action dispatch
already revalidates live state; preserve that. Any cache must invalidate on mount,
unload, address reuse, item/permission/listener changes and selection changes, and
remain bounded after repeated rebuilds. Do not copy global maps or private mutable
properties onto semantic widget records. Do not infer a Continue action from
English text: TSPS contains that heuristic, while our behavior must follow the
240 widget/menu contract. Phases 5/7.

### U3. Separate input ownership from camera gestures — use as test cases

**TS anchors:** `client/game/widgets/input/widgetMenuWheelInput.ts::
processWidgetMenuWheelInput`, `client/game/menu/WorldMenuBuilder.ts` and menu tests.

Scrollable open menus consume wheel input using the same scaled coordinates as
their hit regions. World menu inputs explicitly include spell/item selection,
combat-level attack policy and follower priority. These are useful scenario
inventories for our incomplete shared input/menu port.

Implement validated 240 rules in input/application/game-ui with platform-neutral
events. Keep world picking and input transforms consistent, and ensure foreground
widget/menu ownership prevents camera leakage. The TS callbacks and renderer-owned
interaction architecture are not the Rust design. Menu construction order, stacked
targets, +2000 priorities and packet dispatch still require exact 240 evidence.
Phase 5 under [SPEC-0021](../specs/SPEC-0021-input-menus.md).

### U4. World-map background work and sidebar lifecycle — partly already present

**TS anchors:** `client/game/worker/WorldMapTileJob.ts::{load,cancel,getRenderer}`,
changed `WorldMapController.ts` / `WorldMapArchiveRenderer.ts`, and changed
`client/game/sidebar/SidebarStore.ts`.

Map jobs share an existing cache worker, carry an epoch, cancel obsolete tiles and
yield to foreground scene work. Pixel completion and main-thread responsiveness
are measured separately in TSPS's report. Rust's current map worker and raster
budget already cover part of this; the reusable ideas are foreground priority,
bounded cancellation and shared native/browser orchestration. Retain our cache
adapter for map formats. A 241 map renderer does not by itself validate 240 layout.

SidebarStore remembers the previous panel independently of collapse and avoids
publishing identical state. Rust's retained three-state shell already has the
owning contract; compare restoration/disabled-plugin cases rather than copying
React or introducing another navigation store. Existing shell preference decisions
stay authoritative. Phases 10/12/13.

### U5. Cache-wide format, stack-effect and interface sweeps — strongest tooling lead

**TS anchors:** `client/tests/cache-config-decode.test.ts`,
`client/scripts/cache/{generate-command-signatures,cs2-sweep,interface-sweep}.ts`,
`client/rs/cs2/CommandSignatures.ts`, associated script/interface sweep tests;
`server/scripts/compare-cache.ts` and `docs/cache-revision-update.md`.

Useful mechanisms:

- Decode every entry in selected config archives; report unknown opcodes and exact
  byte consumption, including trailing data. Inventory skipped/missing archives.
- Compare handler stack effects with revision-specific int/object/long signatures,
  both in actual scripts and isolated neutral-input handler runs. Report unchecked
  handlers and context-sensitive exceptions separately.
- Load interfaces, then exercise onLoad/transmit/timer paths with explicit state;
  report newly broken script paths and suspicious item/text output across caches.
- Diff named widget components, varp/varbit definitions and DB columns before a
  cache migration. Literal-only scanners miss constants and alternate UID syntax;
  TSPS documents those blind spots.

Apply these to our selected **240** cache and existing cache/script audit tooling
first, complementing `CS2-HOST-COVERAGE.tsv` and `tools/parity_inventory.py`.
The interpreter already has longs/arrays; DB long columns still explicitly error
in [database.rs](../../crates/application/src/scripts/database.rs). Do not port
241 opcode numbers or generalized DB behavior on resemblance alone.

TSPS's script test asserts stack mismatches/crashes, **not all script errors**;
it carries known shape exceptions. Its interface test asserts script-error absence
for server-opened groups, **not every interface's visual/semantic correctness**;
item-0/null output is reported, not asserted. Neutral stub handlers can satisfy
shape checks. Our reports must preserve those distinctions and keep unsupported
semantics open rather than upgrading dispatch counts into parity. Phases 0/7.

### U6. Formatting, data readiness and event allocation — focused follow-ups

**TS anchors:** `client/rs/font/textTemplates.ts::resolveTextTemplates`,
`client/network/serverConnection/domain/itemPrices.ts`,
`client/runelite/client/RuneLite.ts::{postClientTick,postPostClientTick,postBeforeRender}`,
`EventBus.ts::hasSubscribers`, `client/render/gfx/GfxManager.ts` actor indexes.

The 241 cache update documents `<str_name=value>` / `<str_name>` templates used
consistently in measurement, wrapping and drawing. Audit our actual 240 strings
before adding template support; keep it in the existing text owner, with bounded
expansion/cache and no changes to ordinary `<str>` markup.

Guide prices distinguish loading, ready-without-a-quote, and a value, and reject
late requests from a newer login. This is useful lifecycle design for the missing
GE feature; `/api/item-prices`, loading constants and fallback semantics are TSPS
policy until verified for our profile. Use platform content access and an existing
semantic/application owner, not module globals or plugin-owned economic truth.

Current RuneLite.ts guards three frequent event constructions with subscriber
checks; the earlier performance note's unguarded-event observation is historical.
GfxManager maintains per-actor indexes instead of repeatedly scanning all effects.
Use bounded indexes/interest filtering inside our existing state/bridge owners
where measurements justify them. Core events/replay must still be committed even
with zero plugin subscribers; omission may apply only to unnecessary plugin
projection/allocation. Phases 4/6/8/12.

## Exclusions and correctness traps

| TSPS evidence | Decision for RustClient |
| --- | --- |
| `rs/scene/WallDecorationOffset.ts::{wallDecorationNudge,embeddedWallDecorationShift}` and `render/loc/SceneLocs.ts` callers | Do not adopt their corrective offsets as stock placement. Verify placement order, host displacement, rotation, second plate and final depth independently in exact 240 evidence. The presence of an offset unit test does not establish visual parity. |
| `render/webgpu/shaders/main.vert.wgsl.ts`: model/face priority masked to 3 bits then added to view-space depth; `actor.wgsl.ts::applyPriorityDepthBias` | Reject as a substitute for authored depth bias and source face ordering. Our SPEC-0016 deliberately distinguishes them. |
| `render/webgpu/WorldResources.ts` pipeline construction: depth writes enabled and `less-equal` / punch `always` | Do not transplant pipeline defaults into our reverse-Z, strict-Greater and deferred-opaque-write renderer. Carry optimization mechanisms only after matching our pass contracts. |
| `render/gfx/GfxManager.ts`: `TILE_GFX_LIFT_UNITS=8`, wall-clock/chained-effect grace | Do not infer stock effect heights or lifetimes from these presentation fixes. Effect expiry/slots remain cycle-driven GameState behavior. |
| `rs/cs2/handlers/UnsupportedOps.ts` | Neutral input/output handlers are not implemented semantics. Preserve explicit unsupported gaps or an independently accepted profile policy. |
| `game/worldview/WorldViewManager.ts::createPrimaryWorldView` uses `-1` | Its unchanged world-view code is not evidence for the 240 root-id contract, which uses 0. |
| `game/movement/NpcClientTick.ts::computeMovementStep` uses normalized distance/epsilon; animation controller resets looping state | Do not replace our evidenced 240 per-axis path stepping or action completion with these convenience helpers. Unchanged hashes do not confer authority. |
| `runelite/client/plugins/PluginInjector.ts` exposes the engine via `CLIENT_TOKEN` and global injector context | Exclude from external plugin design. Retain versioned immutable snapshots, capabilities and declarative output under SPEC-0004. Plugin feature scenarios may still be useful. |
| TSPS server quests/combat/skills/content and custom wire IDs | Server authority and custom content are not client gameplay rules or RSProt fixtures. Only port verified client-visible interpretation. |

**Our own decoration reconciliation is still open.**
[decorations.rs](../../crates/scene/src/decorations.rs) currently sets
`FLUSH_DIAGONAL_DECORATIONS = true`, documents a non-client geometric flush, and
[locations.rs](../../crates/scene/src/locations.rs) adds straight-decoration nudges.
SPEC-0016's baseline says decoration snapping is off. This research does not make
either implementation correct or silently accept the difference. Reconcile the
owning spec/source evidence and `depth` matrix row before a future change; preserve
separate authored offsets, projection corrections and depth behavior. User-reported
TSPS offset/depth problems are an exclusion constraint, not a location-by-location
visual diagnosis performed in this review.

## How to use this research within the roadmap

1. **Phase 0/7:** add revision-240 cache/stack/interface audit evidence to the existing
   inventories. This exposes real gaps before more stubs or renderer work hide them.
2. **Phase 3:** profile scene construction/upload and extend the current workers with
   coherent snapshots, cancellation and staged publication where spikes justify it.
3. **Phase 5/7:** use stale-widget, input-ownership and menu scenarios as focused
   acceptance cases while moving semantics into shared owners.
4. **Phases 6/11:** profile actor assembly/posing, then investigate CPU pose reuse and
   conservative preparation culling. GPU label posing needs the precision gate first.
5. **Phase 12/13:** extend damage/event optimizations where measured; evaluate
   instancing, pooling and bundles only after ordering and lifecycle are preserved.

These are research priorities within the canonical phases. No domain/method/packet
ledger is marked more complete by this document, and no new architecture boundary
or deviation is accepted. Any behavior-changing proposal needs SPEC-0019's evidence
and decision path before implementation.

## Performance evidence and validation limits

TSPS's `docs/client-performance-2026-10-23.md` reports bounded uploads, pose reuse,
UI batching and local CPU improvements, including a small isolated bundle result.
Its world-map comparison reports similar tile-completion time with a smaller
main-thread timer gap. `docs/runelite-performance.md` distinguishes selected upload
pixels from bandwidth and synchronous submission time from GPU execution.
Those distinctions are useful benchmarking practice; **their numbers are upstream
claims, not RustClient results**. Raw `/tmp` captures cited there were not supplied
or independently reproduced. Different cache, actor population, textures, CPU/JIT,
browser and presentation cap prevent assigning any expected Rust speedup.

Performed here: architecture/spec and selected implementation inspection, all 13
old-file hash comparisons, selected source pin capture, documentation-index/link
and evidence-integrity checks. No Rust source or reference tree was changed.
Cargo checks/Clippy/tests, TSPS test/typecheck/build, live native/browser gameplay,
visual acceptance and benchmark reruns are **NOT-RUN**. Existing test files and
upstream passing-test reports are not validation of this working tree.

For any later port, use a fixed 240 profile/cache and recorded workload, preserve
committed-state and posed-geometry/picking results, and measure stage CPU p50/p95/p99,
queue age, uploads, draw/bind counts and peak retained memory separately. Rendering,
GPU timing, total worker CPU and input-to-visible latency are different measures.
Follow ADR-0004's bounded visual acceptance; do not turn this research into a
screenshot farm. Retain TSPS's BSD-2-Clause notice and file-specific attribution
if a later implementation derives code, rather than only researching behavior.
