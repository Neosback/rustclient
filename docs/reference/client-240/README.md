# Revision-240 client: readable names mapped to the original

Status: active research tree. Extends [`../rs240-port/`](../rs240-port/README.md); it does not replace
its navigation, ledger or status vocabulary.

## What this tree is

The pinned revision-240 client evidence has stable but unreadable names (`classDF.method3015`). This tree
adds an **evidence-backed readable-name overlay** on top of those stable symbols, together with
per-subsystem write-ups, so ports can cite behavior by a meaningful name and still trace every claim back
to the original obfuscated symbol.

Nothing here edits Java. A name is a line in a mapping shard; the readable sources are regenerated.

```text
original gamepack jar  ──rl-suite──▶  semantic jar (classXX / fieldN / methodN, @ObfuscatedName kept)
                                              │  tiny-remapper + mappings/merged.tiny
                                              ▼
                                       readable jar ──Vineflower──▶ readable sources (.cache, untracked)
```

Every claim can be walked back: readable name → stable symbol (the mapping key) → original obfuscated
name (`@ObfuscatedName` in the jar, unchanged by construction).

## Layout

| Path | Purpose |
| --- | --- |
| `mappings/clusters/NN-name.tiny` | One tiny-v2 shard per cluster. Left column is the stable rl-suite name, right is the readable name. A class appears in exactly one shard. |
| `mappings/merged.tiny` | Generated by `tools/client-240/merge-mappings.sh`. Never hand-edit. |
| `ledger/clusters/NN-name.tsv` | One row per renamed symbol with tier, confidence and evidence. |
| `ledger/NAMES.tsv` | Generated merge of the cluster ledgers. Never hand-edit. |
| `clusters/NN-name.md` | Behavior write-up for the cluster: old→new table, algorithms, wire and cycle semantics, Rust owner, open questions. |
| `proposals/` | Unconfirmed candidate names (for example 235 carry-forward). Not part of the mapping until an agent confirms them. |
| `verification/<wave>.md` | Machine output of `tools/client-240/verify.sh`. |
| `../../../tools/client-240/` | Scripts and the ASM helper. |

## Evidence tiers

Every ledger row records the strongest evidence behind the name. Anything weaker than T4 stays unnamed.

| Tier | Source | Typical confidence |
| --- | --- | --- |
| T1 | RuneLite API getter implemented by the jar that returns one field (`Player.getSkullIcon()` returns `field1269`, so the field is `skullIcon`). Deterministic. | A |
| T2 | Packet tables (`rl-suite-main/data/rev-240/mappings/*-packets.tsv`) and the selected RSProt 240 sources, cross-checked against control flow. | A or B |
| T3 | Carry-forward from the hand-named RuneLite 235 client, accepted only when structure matches (superclass chain, descriptors, constants, call shape). | B |
| T4 | Behavior-derived: a cited method plus a one-line justification, ideally corroborated by cache or wire evidence. | B or C |

RuneLite injection-only members (hooks, callbacks, `@Export` shims) get status `injection-only` in the
cluster write-up and are not named as stock behavior.

## Commands

All run from the repository root. They read the semantic jar from outside the repo; set
`CLIENT240_TOOLS` and `CLIENT240_SEMANTIC_JAR` if your local copies live elsewhere. The pinned SHA-256 of
both jars is checked first.

```text
bash tools/client-240/verify.sh <wave-label>     all checks, writes verification/<wave-label>.md
bash tools/client-240/merge-mappings.sh          regenerate mappings/merged.tiny
bash tools/client-240/remap.sh forward OUT.jar   build the readable jar
bash tools/client-240/decompile.sh IN.jar DIR    regenerate readable sources
```

## What `verify.sh` proves, and what it does not

Proves: shards are valid tiny-v2, every entry names a symbol that exists (with the right descriptor),
no target name collides, the mapping and the ledger agree, remapping forward then back reproduces the
semantic jar's bytecode exactly, every `@ObfuscatedName` and `@ObfuscatedSignature` is unchanged, nothing
under `references/` changed, and the readable jar decompiles.

Does not prove: that a **name is right**. That is why T3 and T4 entries are read by hand against the cited
method before a cluster is committed, and why uncertain names are left generic.

## Caveats

- The semantic jar is analysis-only. rl-suite rewrites three constant-dynamic string-concatenation sites,
  which changes when those constants are computed. Behavior notes about those three constants come from
  the original jar. Never log in with a remapped jar.
- RuneLite injects the client. Separate stock behavior from injection when writing a cluster note.
- A Java class does not become a Rust type one-for-one. Each cluster names its RustClient owner and
  follows the porting rule in [`../rs240-port/README.md`](../rs240-port/README.md).
- Existing client quirks and bugs are recorded as quirks with the method reference, never silently
  corrected, because OpenRune behavior may depend on them.
