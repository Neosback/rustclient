# IF1 button dispatch continuation, 2026-10-29

This continues the [TSPS shortlist](../reference/TSPS-GIT-SHORTLIST-2026-10-29.md)
and [CS1 checkpoint](CS1-240-2026-10-29.md). Stock revision 240 remains the
behavioral authority. This checkpoint implements authored click/toggle/select
button dispatch and local direct-varp assignments; full legacy button lifecycle
and game-option effects are still partial.

## Result and ownership

The existing widget action owner now exposes authored IF1 labels and distinct
click, toggle and select actions. They require a displayed base component, an
authenticated session and a current interface epoch. They cannot borrow ordinary
operation labels, dynamic-child identities or operation permissions. Legacy
buttons do not run an ordinary onOp listener. Existing dialogue continuation is
retained; this checkpoint does not add its missing pending-resume latch.

The existing revision-240 protocol adapter sends IF_BUTTON, opcode 11, with the
four-byte big-endian combined component. It remains separate from the nine-byte
IF_BUTTONX and dialogue-resume packets. Dynamic-child and item context are
rejected before consuming ISAAC state. No TSPS custom packet numbering is copied.

Toggle/select inspect only expression zero's leading direct varp reference,
without evaluating the whole CS1 expression. Toggle wraps `1 - current`; select
uses comparison zero and avoids a redundant assignment. These rules live in the
cache/profile adapter. Application commits through the existing client-variable
transition and variable-listener queue. The server shadow is preserved, so a
subsequent synchronization still restores the server's value. A malformed local
reference retains the already-produced button intent and returns a diagnostic.

Special button actions have no indexed operation number. Target priority accepts
only indexed operations, preventing special actions from entering that retained
field. Existing valid fingerprint bytes are unchanged; there is no new retained
state, event, replay format, plugin ABI or platform-specific implementation.

## Deliberate limits

Click content handlers (logout/appearance and others) reject with a contextual
diagnostic before sending. Target selection and close-dialog lifecycle remain
unimplemented. The pending-continue latch, source menu ordering and complete
native/browser interaction acceptance are separate obligations.

The direct varp assignment is implemented, but `classXQ.method12935` option-type
side effects are not. Each changed assignment reports that gap; no audio,
brightness, attack-option or other preference mutation is guessed. Config group
16 decoding and its option consumers remain open. This is not complete button
or game-option parity. Existing server/client varp synchronization remains the
authoritative owner; no second variable store was added.

The next implementation step is the group-16 VARPLAYER definition and shared
option-effect path (`classGN.method5538`, `classOY`, `classXQ.method12935`).
Apply those effects through the existing variable-update owner for server, CS2
and IF1 changes together; adding a button-only settings store would duplicate
semantic ownership.
